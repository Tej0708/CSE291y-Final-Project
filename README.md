# TickTock Spec→Fuzz — Experiment Package

**Tej Gaonkar · Xuan Zhou — CSE 291P Final Project**

This package contains everything from the spec-driven fuzzing experiment on
TickTock (the Flux-verified Tock OS fork): the spec census, the spec-derived
and plain fuzz harnesses, the minimal spec→harness translator, the mutation
experiments (hand-written + blind cargo-mutants sets), all raw result data,
and the full report.

**Read first**: [`docs/REPORT.md`](docs/REPORT.md) (results & findings) ·
[`docs/census.md`](docs/census.md) (H3) · [`docs/experiment-plan.md`](docs/experiment-plan.md) (the plan we executed)

## Headline results

| Hypothesis | Verdict | Evidence |
|---|---|---|
| H1: spec harnesses ≥ plain fuzzer detection under equal budgets | **Confirmed** | hand-written set 77.8% vs 11.1%; blind cargo-mutants set 42.5% vs 12.6% (signal basis); stable across 30s/120s/300s budgets; coverage 1.4–2.0× |
| H2: a mutant class exists that plain fuzzers cannot detect in principle | **Confirmed** | M3/M6/M8 (identical return values, no panic, ghost-state-only) — plain 0 detections at every budget; spec 100% |
| H3: translatable fraction < 100%, bounded by ghost/higher-order refinements | **Answered, with revision** | 19 fully / 80 partial / 10 untranslatable out of 109 sigs; the hard wall is proof lemmas, while ghost params/`strg`/FluxPtr are recoverable at runtime — and "translatable ≠ detection-capable" (L2 literal specs catch zero discriminating mutants; L3 proof semantics catch all five) |

Key bonus findings: the verified code's in-code Flux assertions are runtime
no-ops (the verified binary has zero runtime protection for its proven
contracts); the verified constructor's `app_break == kernel_break` postcondition
is an implicit precondition nowhere in the specs (F1); non-power-of-two `align`
exposes a real spec gap (F2).

## Quick start

```bash
# inside a tock-flux checkout (branch: the Flux-verified TickTock sources):
#   1. copy fuzz/ to <tock-flux>/fuzz
#   2. apply kernel-patch/README.md diffs (shim + 3 visibility changes + workspace exclude)
export PATH="$HOME/.cargo/bin:$PATH"
export CARGO_TARGET_DIR=/tmp/fuzz-target        # local disk!
export AR=<toolchain>/lib/rustlib/x86_64-unknown-linux-gnu/bin/llvm-ar

cd fuzz && cargo fuzz build --sanitizer none
$CARGO_TARGET_DIR/x86_64-unknown-linux-gnu/release/allocate_in_grant_region_spec -max_total_time=30
```

Toolchain: nightly-2025-03-14 (pinned by tock-flux's rust-toolchain.toml);
`cargo-fuzz` 0.13+, `cargo-mutants` 27+ for the blind set. Full reproduction
commands for every experiment are in `docs/REPORT.md` §9.

## Host quirks we hit (save yourself the debugging)

- Keep build artifacts on **local disk** — NFS corrupted archives (`ar` SIGBUS) and link jobs on our host.
- NFS mtime granularity is ~1s: the runners bump mtimes after patching so cargo doesn't silently skip rebuilds (otherwise you measure the original binary).
- The build-then-run discipline in the runners is mandatory: binaries are only valid until the next source patch.
